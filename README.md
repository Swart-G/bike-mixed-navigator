# Смешанный навигатор

Web-навигация по Москве для поездок с **собственным велосипедом + общественным транспортом**.

Главная идея проекта — искать не обычный маршрут `пешком → транспорт → пешком`, а комбинировать:

```text
велосипед → автобус / трамвай / поезд → велосипед
```

При этом велосипед рассматривается не только как способ добраться до ближайшей остановки. Маршрутизатор пытается найти точки, где выгодно:

- доехать до более удобного транспорта на велосипеде;
- проехать основную часть пути на общественном транспорте;
- выйти раньше конечной точки и продолжить на велосипеде;
- заменить пешие участки велосипедом;
- убрать короткие и неэффективные участки общественного транспорта;
- сохранить длинные полезные участки автобуса, трамвая или поезда.

Текущая версия routing pipeline: **v0.8**

---

## Возможности

### Карта и интерфейс

- карта Москвы на MapLibre GL JS;
- выбор старта и финиша кликом по карте;
- перетаскиваемые маркеры;
- поиск адресов через Nominatim;
- автоматическая выдача большого набора разных стратегий без настроек поездки;
- отдельная геометрия каждого участка;
- цветовое разделение велосипеда и общественного транспорта;
- короткий список маршрутов слева;
- плавающая подробная карточка выбранного маршрута поверх карты;
- навигация по участкам с автоматическим приближением карты;
- ручная замена любого непрерывного диапазона участков на новый безопасный
  велосипедный маршрут;
- проверка, что ручная замена не ломает последующую посадку на фиксированный
  рейс, и возможность отменить изменение;
- пронумерованные места смены участков на карте;
- выбор времени отправления;
- выбор точек на карте только после нажатия соответствующей кнопки.

На мобильных экранах карта занимает весь viewport, варианты выводятся
горизонтальной лентой снизу, а подробности и ручное редактирование открываются
как нижняя панель. Все основные интерактивные элементы имеют touch-размер не
менее 40–44 px и учитывают safe-area.

### Поддерживаемый транспорт

Сейчас используются:

```text
BUS
TRAM
TROLLEYBUS
RAIL
SUBWAY
```

Конкретный режим используется только если он присутствует в загруженном GTFS.

### Велосипедные стратегии

Пользователь больше не выбирает стиль/скорость поездки. На каждый запрос одновременно строятся разные bicycle-гипотезы:

| Стратегия | Приоритет |
|---|---|
| Прямее | Более короткий безопасный велосипедный коридор |
| По велодорожкам | Велодорожки и безопасная инфраструктура |
| Тихий маршрут | Максимальный safety weight |

Все варианты используют режим OTP `BICYCLE`; автомобильные legs (`CAR`, `MOTORCYCLE`) отклоняются. Для ETA используется единая эффективная средняя скорость городской поездки. Она приблизительно учитывает:

- светофоры;
- переходы;
- перекрёстки;
- торможения;
- разгоны;
- короткие остановки;
- городской ритм движения.

В будущем эта аппроксимация должна быть заменена более точными штрафами для конкретных перекрёстков и объектов OSM.

# Как строится маршрут

## 1. Прямой велосипедный маршрут

Всегда рассчитывается baseline:

```text
A ───────── 🚲 ───────── B
```

Он нужен для сравнения со смешанными вариантами.

---

## 2. Transit-first route

Основная логика сначала строит обычный маршрут общественного транспорта:

```text
WALK → BUS → WALK → TRAM → WALK
```

После этого маршрут оптимизируется под велосипед.

### Пешие участки

Каждый WALK-leg проверяется отдельно:

```text
WALK
 ↓
можно ли быстрее проехать между теми же точками на велосипеде?
 ↓
BICYCLE
```

Если велосипед быстрее — пеший участок заменяется.

---

## 3. Проверка участков общественного транспорта

Отдельные короткие BUS/TRAM/RAIL участки сравниваются с велосипедом.

Однако общественный транспорт считается **основным скелетом маршрута**.

Поэтому длинный участок транспорта не удаляется только потому, что велосипед математически оказывается быстрее между его остановками.

Например:

```text
🚋 7 км
```

не должен автоматически превращаться в:

```text
🚲 4 км
```

даже если OTP считает велосипед немного быстрее.

Удаляются только действительно короткие и неэффективные transit-leg.

---

## 4. Egress Anchor Search

Это один из главных механизмов проекта.

Обычный OTP может выбрать:

```text
велосипед → трамвай → велосипед
```

но пропустить более интересный вариант:

```text
велосипед
    ↓
автобус
    ↓
выйти ближе к центру
    ↓
велосипед по удобным улицам
```

Backend самостоятельно анализирует GTFS и выбирает перспективные остановки около конечной точки.

Для них проверяются маршруты вида:

```text
Origin
   ↓
общественный транспорт
   ↓
Anchor stop
   ↓
велосипед
   ↓
Destination
```

Обычно рассматривается несколько расстояний от финиша, а не только ближайшие остановки.

---

## 5. Multi-query Candidate Generator

Один пользовательский запрос превращается в несколько параллельных запросов OTP.

Например:

```text
весь транспорт
BUS-only
TRAM-only
RAIL-only
несколько bicycle street strategies
```

Это помогает не зависеть от одного локального optimum OTP.

---

## 6. Diversity Selector

Если OTP нашёл:

```text
1. трамвай 47
2. трамвай 47
3. трамвай 47
4. трамвай 47
```

пользователю не нужны четыре почти одинаковых варианта.

Маршруты группируются по transit-chain.

В финальной выдаче сохраняется до четырнадцати разных стратегий:

```text
самый быстрый
лучший по score
лучший автобусный
лучший трамвайный
лучший железнодорожный
лучший transport → bicycle
прямой велосипед
```

Настроек стиля, упора и количества пересадок в интерфейсе нет. Один запрос
одновременно запускает ближние и дальние boarding/egress anchors, несколько
временных окон OTP, разные ограничения транспортного skeleton и все семейства
оптимизации сегментов — от transit-heavy до bike-heavy. Поэтому пользователю
сразу показываются быстрые, магистральные, железнодорожные, велосипедные и
другие разумные стратегии.

Similarity clustering сравнивает транспортную цепочку, коридор, остановки
посадки и выхода, велосипедную геометрию и происхождение кандидата. Почти
одинаковые варианты не возвращаются даже ради искусственного увеличения числа
карточек. Лучший вариант каждого действительно отличающегося коридора защищён
от глобального Pareto dominance.

Отдельно сохраняются крайние стратегии: прямые маршруты полностью на велосипеде
и исходные transit-first маршруты без обязательной замены подходов велосипедом.
Поэтому в выдаче могут одновременно присутствовать полностью велосипедный вариант
и вариант, почти целиком состоящий из общественного транспорта.

Для автобусов учитываются не только время и частота, но и класс линии. Маршруты с
московскими префиксами `м/m` и `е/e`, а также явно быстрые автобусные линии получают
дополнительный приоритет как магистральные или экспрессные. Финальный лимит выдачи —
до 20 непохожих маршрутов.

Слева отображается короткое резюме каждого маршрута. Подробности выбранного
варианта находятся в плавающей карточке над картой; кнопки «назад» и «вперёд»
переключают участки и приближают их геометрию.

Обычный клик по карте ничего не меняет. Режим установки точки включается только
кнопкой «На карте» рядом с полем «Откуда» или «Куда» и выключается сразу после
установки маркера.

# Scoring

Финальный выбор делает не только OTP.

Backend дополнительно учитывает:

```text
door-to-door time
initial wait
ожидание транспорта
количество пересадок
посадки с велосипедом
пешую дистанцию
длину transit-leg
полезность общественного транспорта
```

Слишком короткий общественный транспорт получает penalty.

Например:

```text
🚲 5.4 км
🚌 330 м
🚲 1.3 км
```

считается подозрительным маршрутом и получает штраф.

# Данные

## OpenStreetMap

Используется для:

- велосипедной маршрутизации;
- дорожной сети;
- разрешённых направлений движения;
- велосипедных тегов;
- геометрии улиц.

Пример файла:

```text
data/moscow.osm.pbf
```

## GTFS

Используется для:

- маршрутов;
- остановок;
- конкретных рейсов;
- расписания;
- времени прибытия к остановкам;
- календаря движения.

Пример:

```text
data/moscow-gtfs.zip
```

### Важное замечание про велосипед

Для работы:

```text
BICYCLE → TRANSIT → BICYCLE
```

OTP требует явного разрешения перевозки велосипеда в GTFS.

В текущем тестовом наборе данных `bikes_allowed` был временно выставлен в `1` для всех trips.

Это **техническая заглушка**, а не реальные правила Москвы.

Перед production-версией нужен отдельный **Bike Policy Compiler**, который будет задавать разрешение на провоз велосипеда согласно реальным правилам конкретного транспорта.

# Realtime

Сейчас используется обычный статический GTFS.

То есть учитываются:

- расписание;
- конкретный рейс;
- время движения между остановками;
- календарь движения.

Но пока не учитываются:

- фактические задержки;
- GPS автобусов;
- отмены рейсов;
- пробки общественного транспорта.

OTP поддерживает GTFS-Realtime, но для текущего московского источника публичный стабильный GTFS-RT endpoint пока не подключён.

# Docker Compose

Пример:

```yaml
services:
  otp:
    image: bike-mixed-navigator-otp:local
    build:
      context: .
      dockerfile: Dockerfile.otp
      no_cache: true
    container_name: otp-moscow

    ports:
      - "8080:8080"

    environment:
      JAVA_TOOL_OPTIONS: "-Xmx8g"

    healthcheck:
      test:
        - CMD
        - /usr/bin/bash
        - -ec
        - >-
          exec 3<>/dev/tcp/127.0.0.1/8080;
          printf 'GET /otp/actuators/health HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' >&3;
          head -n 1 <&3 | grep -qE '^HTTP/[0-9.]+ 200 '
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 10m

    restart: unless-stopped


  web:
    build: ./web
    container_name: mixed-navigator-web

    ports:
      - "5000:5000"

    environment:
      OTP_URL: "http://otp:8080/otp/gtfs/v1"
      GTFS_PATH: "/otp-data/moscow-gtfs.zip"
      OTP_FEED_ID: "1"
      NOMINATIM_USER_AGENT: "MixedNavigatorPrototype/0.4"

    volumes:
      - ./data:/otp-data:ro

    depends_on:
      otp:
        condition: service_healthy

    restart: unless-stopped
```

# OTP readiness

Actuator API, который используется Docker healthcheck, включается в
`otp-config.json`:

```json
{
  "otpFeatures": {
    "ActuatorAPI": true
  }
}
```

Endpoint `/otp/actuators/health` начинает отвечать `200` только после загрузки
графа и готовности updaters. До этого web-контейнер не запускается, а
`POST /api/routes` при недоступности OTP возвращает `503` с кодом
`OTP_UNAVAILABLE`.

# Построение OTP graph

`graph.obj` строится в отдельном этапе `Dockerfile.otp` из
`data/moscow.osm.pbf` и `data/moscow-gtfs.zip`, а затем копируется в финальный
образ OTP. В `docker-compose.yaml` для этого образа включён `no_cache: true`,
поэтому обычный полный запуск каждый раз пересобирает граф с нуля:

```bash
docker compose up -d --build
```

Старый `data/graph.obj`, если он остался от предыдущей схемы запуска, не
используется и не монтируется в контейнер. Сервис `otp` стартует только из нового
образа после успешного завершения build-этапа, а `web` по-прежнему ждёт healthy
статуса OTP.

# Мягкие ошибки OTP

Candidate Generator намеренно делает несколько узких запросов.

Например `RAIL-only` может вернуть:

```text
NO_STOPS_IN_RANGE
```

хотя автобусный вариант успешно существует.

Поэтому следующие ошибки считаются мягкими:

```text
NO_STOPS_IN_RANGE
NO_TRANSIT_CONNECTION
NO_TRANSIT_CONNECTION_IN_SEARCH_WINDOW
WALKING_BETTER_THAN_TRANSIT
```

Они скрываются от пользователя, если общий поиск всё равно нашёл пригодные маршруты.

# Геокодинг

Поиск адресов пока использует публичный Nominatim.

Чтобы не создавать лишнюю нагрузку:

- запрос выполняется только по Enter/кнопке;
- autocomplete отсутствует;
- backend кэширует ответы;
- между запросами выдерживается ограничение частоты.

Для production-развёртывания лучше использовать собственный geocoder или отдельного провайдера.

# Известные ограничения

## Нет точного Bicycle Stress

OTP учитывает OSM bicycle-модель, но наш backend пока не анализирует подробно:

- выделенные велодорожки;
- велополосы;
- магистрали;
- качество покрытия;
- количество полос;
- `maxspeed`;
- опасные пересечения.

Поэтому различие стратегий сейчас определяется safety/time weights OTP. Для жёсткого
разделения велодорожек и улиц общего пользования в будущем потребуется отдельная
OSM-атрибутика в ответе или специализированная велосипедная street-модель.

## Нет точных задержек на перекрёстках

Светофоры и городской ритм сейчас приблизительно учитываются уменьшенной эффективной средней скоростью.

Позже планируется использовать OSM:

```text
highway=traffic_signals
crossing=*
junction=*
```

и добавлять реальные penalties для маршрута.

## Нет realtime

Нет GTFS-RT.

## Нет Bike Policy Compiler

Пока используется тестовое разрешение велосипеда в общественном транспорте.

## Egress Anchors есть, Boarding Anchors ещё нет

Уже можно специально искать:

```text
транспорт → велосипед
```

но ещё нет полноценного обратного механизма:

```text
велосипед → более выгодная остановка → транспорт
```

# Статус проекта

Проект находится на стадии функционального прототипа.

Основная связка уже работает:

```text
OSM
+
GTFS
+
OpenTripPlanner
+
собственный Candidate Generator
+
Transit-first Optimizer
+
Egress Anchors
+
Web UI
```

Основная задача следующих версий — уже не доказать возможность смешанной маршрутизации, а сделать **качество выбора маршрутов заметно лучше обычного OTP для сценария поездки с собственным велосипедом**.
